# 14日後に何を見て、何を決めるか

**先に決めておく。** データが出てから基準を作れば、どんな結果でも「続ける理由」が書ける。

判定日：**公開から14日**（GitHub の traffic API は14日しか保持しないため、
`npm run metrics` で日次スナップショットを `metrics/` に残す）

## 見る指標

| 指標 | 何を意味するか |
|---|---|
| **unique clones** | **本命。** 実際に手元へ置いた数。README を読んだだけでは増えない |
| unique views | 到達 |
| referrers | どこから来たか。**MCP ディレクトリ経由なら開発者、検索経由なら実務者** |
| paths | README を読んだだけか、`data/cases.json` まで取ったか |

## 決めること

| 観測 | 判断 |
|---|---|
| unique clones ≥ 25 かつ referrers に MCP ディレクトリ2つ以上 | **続ける。** ホスト版の常時最新 feed を作る |
| unique clones 5〜24 | **流通を1回だけ変える。** referrers を見て、効いていない経路を捨てる |
| unique clones < 5 | **Kill。** 製品の否定ではなく流通の否定として記録する |

## referrers が答える最大の疑問

この案の最弱点は、**「開発者が入れる」から「会社が払う」への橋**である。
月1.1万〜50万円の広告審査ツールを買うのはマーケターや法務で、
GitHub でこれを見つける開発者と同一人物ではない。

referrers がそこを実測する。

- **MCP ディレクトリ経由が多い** → 開発者に届いている。有料化するなら開発者向けの API か feed
- **検索経由（「景品表示法 措置命令 一覧」等）が多い** → 実務者に届いている。有料化するなら実務者向けの通知や全文検索
- **どちらも無い** → 流通が成立していない。製品を触る前に流通を変える

## 収益はまだ測らない

**14日で測るのは需要の有無だけ。** 課金導線は作っていない。
無料のデータセットと MCP が流通そのもので、
有料化（常時最新 feed・差分通知・PDF の全文）は clones が出てから設計する。
