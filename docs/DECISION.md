# 14日後に何を見て、何を決めるか

**先に決めておく。** データが出てから基準を作れば、どんな結果でも「続ける理由」が書ける。

判定日：**公開から14日**（GitHub の traffic API は14日しか保持しないため、
`npm run metrics` で日次スナップショットを `metrics/` に残す）

## 測っているのは2つの別の問いである

| | 指標 | 答える問い |
|---|---|---|
| **需要** | unique clones / **.mcpb ダウンロード数** / unique views / referrers | **使われるか** |
| **支払意思** | `commercial.html` の uniques / Issue #1〜#5 の 👍 / コメント | **金を払うか** |

**導入は2つの経路で起きる。** `git clone` と、**MCP Registry からの .mcpb ダウンロード**である。
Registry 経由の導入は clone にもGitHubのtrafficにも現れないので、
**clones だけを見ると Registry からの導入がゼロに見える。** 両方を足して読む。

**clones は支払意思の指標ではない。** clone する側の費用はゼロなので、
何件 clone されても、こちらが費用を負担する部分（ホスティング・日次更新・保証）に
金が出るかどうかは何も分からない。だから **Issue #1〜#5 には価格を書いた。**
無料のものへの 👍 と、価格が書かれたものへの 👍 は、別の情報である。

### 各指標の読み方

| 指標 | 何を意味するか |
|---|---|
| **unique clones** | 手元へ置いた数。README を読んだだけでは増えない |
| **.mcpb ダウンロード数** | **MCP Registry 経由の導入。clone には一切出ない別経路** |
| unique views | 到達 |
| **referrers** | **MCP ディレクトリ経由なら開発者、検索経由なら実務者** |
| paths | README で止まったか、`data/cases.json` まで取ったか |
| **commercial.html uniques** | 無料部分を通り過ぎて有料の話を読んだ数。**GitHubアカウント不要なので、開発者でない購買者を捕まえる** |
| **Issue の 👍** | 価格に対して手が挙がった数。5案のどれが要るかを分離する |
| **Issue のコメント** | 用途・頻度・件数を書く手間を払った数。**👍 より重い。1件でも実在の需要** |

## 失敗を3つに分ける

**clones < 5 だけで製品を Kill しない。** 同じ「数字が出ない」が3つの別の原因から起きるので、
どれなのかを referrers と commercial.html で切り分ける。

### A. Distribution failure — 誰も見ていない

**判定：** unique views < 30 **かつ** referrers に MCP ディレクトリが無い

見られていないのだから、製品も課金も否定されていない。
**Kill しない。流通だけを変える。**
MCP ディレクトリへの PR、検索で見つかる形（処分事例ページの静的生成）、
関連コミュニティへの1回の告知のうち、**まだ試していないものを1つだけ**足す。
製品には触らない。

### B. Problem failure — 見られたが、要らない

**判定：** unique views ≥ 30 **かつ** unique clones + .mcpb DL < 5

到達しているのに手元へ置かれない。**痛みの仮説が外れている。**
「広告審査 AI が実在の処分を引用できない」という前提が、
実際には痛みではなかったということ。**ここで Kill する。**
流通を足しても直らないし、有料版を作れば損失が増える。

記録すること：**この題材（官公庁が出さない構造化データ）の型そのものが死んだのか、
それとも景品表示法という題材が死んだのか。** 前者なら次の Venture も避ける。
後者なら型は残る。

### C. Monetization failure — 使われるが、金は出ない

**判定：** unique clones + .mcpb DL ≥ 10 **かつ** 👍 合計 0 **かつ** commercial.html uniques < 5

**製品は当たっている。収益仮説だけが死んでいる。**
無料のデータセットとしては成立しているので、**製品は Kill しない。**
消すのは「これ自体を売る」という筋で、残る選択は2つ:

1. **維持だけして流通資産として持つ** — 費用はほぼゼロ（月1回の再取得のみ）。
   MCP 経由で名前が知られること自体を、後続 Venture の入口として使う
2. **収益の出どころを変える** — 開発者に売るのを止め、
   referrers が実務者を指しているなら実務者向けの形（通知・全文検索）へ寄せる

**どちらにしても、有料版の本開発には進まない。**

### 続ける条件

**判定：** unique clones + .mcpb DL ≥ 25 **かつ** 外部経路（MCP Registry / ディレクトリ / 検索）2つ以上
**または** 👍 が1案に3件以上 **または** コメントで具体的な用途が1件以上

**その1案だけを作る。** 5案とも作らない。
コメント1件のほうが 👍 10件より強い証拠なので、
コメントが出た案は clones が基準に届かなくても作る。

## referrers が答える最大の疑問

この案の最弱点は、**「開発者が入れる」から「会社が払う」への橋**である。
月1.1万〜50万円の広告審査ツールを買うのはマーケターや法務で、
GitHub でこれを見つける開発者と同一人物ではない。

- **MCP ディレクトリ経由が多い** → 開発者に届いている。売るなら API か feed
- **検索経由が多い** → 実務者に届いている。売るなら通知や全文検索
- **どちらも無い** → A（Distribution failure）。製品を触る前に流通を変える

## 14日待たない

判定日まで観測だけして待つことはしない。
**価格を書いた Issue と `commercial.html` は公開初日から出しており、
支払意思の測定は需要の測定と同時に走っている。**
14日後に読むのは、そのあいだに溜まった両方の数字である。
